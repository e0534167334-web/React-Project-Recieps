# הסבר השרת במילים פשוטות

לפי דרישות הפרויקט, מותר להיעזר ב־AI לבניית השרת, אבל צריך לדעת להסביר אותו באופן בסיסי:
לאיזה API ה־React פונה, מה נשלח לשרת, מה חוזר ממנו, איך המידע נשמר, ואיך עובדות ההתחברות וההרשאות.
המסמך הזה עונה על השאלות האלה. בסופו יש שאלות שכדאי להתכונן אליהן.

---

## 1. התמונה הגדולה

המערכת בנויה משלושה חלקים, וכל אחד רץ במקום אחר:

```
 הדפדפן                     השרת (Render)                  מסד הנתונים (Supabase)
┌──────────────┐   HTTP    ┌──────────────────────┐   SQL   ┌──────────────────────┐
│ אתר React    │ ───────▶ │ Node.js + Express    │ ──────▶ │ PostgreSQL           │
│ (מה שרואים)  │ ◀─────── │ (בודק, מחליט, מחזיר)  │ ◀────── │ (שומר את כל המידע)    │
└──────────────┘   JSON    └──────────────────────┘ Prisma  └──────────────────────┘
                                     │
                                     ▼
                            Supabase Storage (קבצי תמונות)
```

- **אתר ה־React** מציג מסכים ושולח בקשות. הוא לא מחליט מה מותר, ולא שומר מידע קבוע.
- **השרת** מקבל כל בקשה, בודק שהיא תקינה ושמותר לבצע אותה, קורא או כותב במסד הנתונים, ומחזיר תשובה בפורמט JSON.
- **מסד הנתונים** הוא המקום היחיד שבו המידע נשמר לאורך זמן.

**למה צריך שרת באמצע?** כי לאתר ה־React אי אפשר לסמוך: כל אחד יכול לפתוח את כלי המפתחים בדפדפן ולשלוח בקשה כרצונו. רק השרת יכול לאכוף כללים, כמו "רק הכותבת עורכת את המתכון שלה".

---

## 2. מה זה API ואיך נראית בקשה

API הוא אוסף של כתובות שהשרת מגדיר. כל כתובת עושה פעולה אחת.

כל בקשה מורכבת מ:

| חלק | מה זה | דוגמה |
| --- | --- | --- |
| Method | סוג הפעולה | `GET` קבלה, `POST` יצירה, `PATCH` עדכון חלקי, `DELETE` מחיקה |
| URL | הכתובת | `/api/recipes/5` |
| Headers | מידע נלווה | `Authorization: Bearer <token>` |
| Body | הנתונים שנשלחים (ב־POST וב־PATCH) | `{ "title": "שקשוקה", ... }` |

והתשובה מורכבת מ:

| חלק | מה זה | דוגמה |
| --- | --- | --- |
| Status Code | האם הצליח, ואם לא, למה | `200` הצליח, `201` נוצר, `400` נתונים שגויים, `401` לא מחובר, `403` אין הרשאה, `404` לא נמצא |
| Body | המידע שחוזר, ב־JSON | `{ "recipe": { "id": 5, ... } }` |

את כל הכתובות אפשר לראות ולנסות ב־Swagger: `/api-docs`.

## 3. המסלול של בקשה אחת, מההתחלה עד הסוף

דוגמה: משתמשת מוסיפה מתכון. ה־React שולח `POST /api/recipes` עם ה־Token ועם פרטי המתכון.

| שלב | מה קורה | איפה בקוד |
| --- | --- | --- |
| 1 | הבקשה מגיעה לשרת, והשרת מוצא את הכתובת המתאימה | `src/routes/index.ts` |
| 2 | **אימות:** בודקים שיש Token תקין ומזהים מי המשתמשת. אם אין, חוזר 401 | `src/middleware/auth.ts` |
| 3 | **ולידציה:** בודקים שכל השדות תקינים (שם של 2 תווים לפחות, רמת קושי מתוך הרשימה וכו'). אם לא, חוזר 400 עם הסבר לכל שדה | `src/schemas/recipes.ts` |
| 4 | ה־Controller מעביר את הנתונים לשכבת הלוגיקה | `src/controllers/recipes.controller.ts` |
| 5 | **לוגיקה:** בודקים שהקטגוריה קיימת, מפצלים את הרכיבים לשורות, ומחליטים על הסטטוס: אם יש תמונה או סרטון במתכון ציבורי, הוא "ממתין לאישור" | `src/services/recipes.service.ts` |
| 6 | **שמירה:** Prisma כותב את המתכון ואת הרכיבים שלו למסד הנתונים | `src/db/prisma.ts` |
| 7 | **תשובה:** השרת מחזיר 201 עם המתכון החדש, בלי מידע פרטי | `src/lib/serializers.ts` |
| * | אם משהו נכשל באחד השלבים, השגיאה מגיעה למקום אחד שמחזיר אותה במבנה אחיד | `src/middleware/errorHandler.ts` |

**למה הקוד מחולק לשכבות?** כל שכבה אחראית על דבר אחד: Routes על הכתובות, Middleware על בדיקות שחוזרות בהרבה כתובות, Schemas על תקינות, Services על הכללים העסקיים. כך קל למצוא תקלה ולשנות דבר אחד בלי לשבור דבר אחר.

## 4. איך המידע נשמר

המידע נשמר ב־**PostgreSQL**, מסד נתונים של טבלאות, שרץ ב־Supabase. השרת מדבר איתו דרך **Prisma**: ספרייה שמאפשרת לכתוב `prisma.recipe.create(...)` במקום לכתוב SQL בעצמנו.

מבנה הטבלאות מוגדר בקובץ אחד: `prisma/schema.prisma`. כל שינוי במבנה נשמר כ־**Migration** בתיקייה `prisma/migrations`: קובץ SQL שיוצר או משנה טבלאות. בעליית השרת בענן, הפקודה `prisma migrate deploy` מריצה את ה־Migrations שעוד לא הורצו.

### הטבלאות והקשרים ביניהן

```
users ─┬─< recipes ─┬─< recipe_ingredients      (לכל מתכון הרבה רכיבים)
       │            ├─< saved_recipes >── users (הספר שלי: משתמש ↔ מתכון)
       │            └── categories              (לכל מתכון קטגוריה אחת)
       ├─< forum_questions ─< forum_answers     (לכל שאלה הרבה תשובות)
       └─< notifications                        (לכל משתמש הרבה התראות)
```

`─<` פירושו "אחד להרבה". למשל: למשתמשת אחת יכולים להיות הרבה מתכונים, אבל לכל מתכון יש כותבת אחת.

| טבלה | מה נשמר בה |
| --- | --- |
| `users` | משתמשים: אימייל, Hash של הסיסמה, שם תצוגה, תפקיד, פרטי קשר |
| `categories` | רשימת הקטגוריות. רק המנהל משנה אותה |
| `recipes` | מתכונים: שם, קטגוריה, קושי, סוג, זמן הכנה, נראות, סטטוס אישור |
| `recipe_ingredients` | רכיב בכל שורה, לפי הסדר. כך אפשר לסנן "מתכונים עם ביצים" |
| `saved_recipes` | אילו מתכונים כל משתמשת שמרה לספר שלה |
| `forum_questions`, `forum_answers` | הפורום |
| `notifications` | התראות אישיות |

**שתי שכבות הגנה על הנתונים:** השרת בודק תקינות לפני השמירה (Zod), ובנוסף מסד הנתונים עצמו אוכף כללים: אימייל ייחודי, זמן הכנה בין 1 ל־1440 דקות, מתכון חייב קטגוריה קיימת. גם אם יש באג בשרת, מסד הנתונים לא יקבל ערך לא חוקי.

**תמונות** לא נשמרות במסד הנתונים. הקובץ עצמו נשמר ב־Supabase Storage, ובטבלה נשמר רק הנתיב אליו.

## 5. איך עובדת ההתחברות

### הרשמה

1. ה־React שולח `POST /api/auth/register` עם שם, אימייל וסיסמה.
2. השרת **לא שומר את הסיסמה עצמה**. הוא מעביר אותה דרך **bcrypt** ושומר רק את ה־**Hash**: מחרוזת שאי אפשר לשחזר ממנה את הסיסמה.
3. המשתמשת נוצרת תמיד כמשתמשת רגילה (`USER`). אי אפשר להירשם כמנהל.

### כניסה

1. ה־React שולח `POST /api/auth/login` עם אימייל וסיסמה.
2. השרת מחשב Hash לסיסמה שהתקבלה ומשווה ל־Hash השמור.
3. אם הם תואמים, השרת יוצר **JWT**: "תעודה" דיגיטלית שבה כתוב מספר המשתמשת, חתומה במפתח סודי (`JWT_SECRET`) שרק השרת מכיר. התעודה תקפה ל־24 שעות.
4. ה־React שומר את ה־Token ושולח אותו בכל בקשה בכותרת `Authorization: Bearer <token>`.

### בכל בקשה מוגנת

1. השרת בודק את החתימה. אם מישהו שינה את ה־Token, החתימה לא תתאים, וחוזר **401**.
2. אם התוקף פג, חוזר **401**.
3. השרת טוען את המשתמשת ממסד הנתונים לפי המספר שב־Token. כך התפקיד נלקח תמיד ממסד הנתונים העדכני, ולא ממה שכתוב ב־Token.

**למה אי אפשר לזייף Token?** כי כדי לחתום עליו צריך את `JWT_SECRET`, שנמצא רק בשרת, במשתני הסביבה ב־Render. הוא לא נמצא בקוד, לא ב־GitHub ולא ב־React.

**למה כשהאימייל לא קיים חוזרת אותה הודעה כמו בסיסמה שגויה?** כדי לא לגלות למי שמנסה לפרוץ אילו אימיילים רשומים במערכת.

## 6. איך עובדות ההרשאות

| בדיקה | השאלה | אם לא, חוזר |
| --- | --- | --- |
| **אימות** (Authentication) | מי את? יש Token תקין? | 401 |
| **הרשאה** (Authorization) | מותר לך לעשות את זה? | 403 |

שלושה סוגי כללים:

1. **לפי תפקיד:** פעולות כמו תור האישורים וניהול קטגוריות מותרות רק ל־`ADMIN`. משתמשת רגילה מקבלת 403.
2. **לפי בעלות:** לעריכת מתכון, השרת בודק שמספר הכותבת שווה למספר המשתמשת המחוברת. המספר נלקח מה־Token, **לא** ממה שה־React שולח, ולכן אי אפשר להתחזות.
3. **לפי נראות:**

| מתכון | אורח | הכותבת | משתמשת אחרת | מנהל |
| --- | --- | --- | --- | --- |
| ציבורי ומאושר | ✓ | ✓ | ✓ | ✓ |
| פרטי | – | ✓ | – | ✓ |
| ממתין לאישור או נדחה | – | ✓ | – | ✓ |

כשמישהו מבקש מתכון שאסור לו לראות, חוזר **404** ולא 403. כך לא נחשף אפילו שהמתכון קיים.

ברשימת המתכונים: ברירת המחדל מציגה מתכונים ציבוריים. משתמשת מחוברת יכולה לבקש `scope=visible` (שלה + הציבוריים), ומנהל יכול לבקש `scope=all` (כל הרשומות). גם ברשימת השאלות בפורום המנהל יכול לבקש `scope=all`, ולראות את כל השאלות בכל סטטוס.

**חשוב:** ב־React מסתירים כפתורים לפי הרשאה (למשל "עריכה" רק לכותבת). זו רק נוחות. ההגנה האמיתית היא בשרת.

## 7. אישור מנהל והתראות

**הכלל:** תוכן ציבורי (מתכון, שאלה או תשובה) שיש בו תמונה או קישור לסרטון נשמר בסטטוס `PENDING` (ממתין), ומוצג רק לכותבת ולמנהל. גם **כל עריכה** של תוכן כזה מחזירה אותו לממתין, כדי שאי אפשר יהיה לשנות תוכן אחרי שאושר.

**התהליך:**
1. המנהל רואה את התור: `GET /api/admin/pending`.
2. מאשר או דוחה: `PATCH /api/admin/moderation/recipes/7` עם `{ "decision": "APPROVED" }`.
3. השרת משנה את הסטטוס ויוצר **התראה** לכותבת: שורה בטבלה `notifications`.
4. ה־React בודק מדי פעם אם יש התראות חדשות ומציג את המספר על הפעמון.

**התראה על תשובה חדשה:** כשמתפרסמת תשובה לשאלה, השרת יוצר התראה לכותבת השאלה. אם התשובה ממתינה לאישור, ההתראה נוצרת רק אחרי האישור.

## 8. חיפוש וסינון

כל החיפוש והסינון נעשים **בשרת**, במסד הנתונים, ולא ב־React. למה? כי ייתכנו אלפי מתכונים, ואין טעם לשלוח את כולם לדפדפן. השרת מחזיר עמוד אחד (12 מתכונים כברירת מחדל) ואת המספר הכולל.

**סינון לפי מצרכים:** כל רכיב שמור בשורה נפרדת. לבקשה `?ingredients=ביצים,קישוא` השרת מחזיר רק מתכונים שיש בהם רכיב שמכיל "ביצ" **וגם** רכיב שמכיל "קישוא". השרת מקצר את המילה כדי שיחיד ורבים יתאימו.

## 11. שאלות שכדאי להתכונן אליהן

**איך ה־React יודע מי מחובר?**
אחרי הכניסה הוא שומר את ה־Token. בטעינת האתר הוא שולח `GET /api/auth/me`, והשרת מחזיר את פרטי המשתמשת לפי ה־Token.

**מה ההבדל בין 401 ל־403?**
401: השרת לא יודע מי את (אין Token, או שהוא לא תקין). 403: השרת יודע מי את, אבל אסור לך לבצע את הפעולה.

**איפה נשמרת הסיסמה?**
הסיסמה עצמה לא נשמרת בשום מקום. נשמר רק ה־Hash שלה, בטבלה `users`.

**מה קורה אם משתמשת משנה ב־React את מספר הכותבת ושולחת עריכה?**
כלום. השרת לא משתמש במספר שנשלח. הוא לוקח את מספר המשתמשת מה־Token ומשווה למספר הכותבת השמור במסד הנתונים.

**איך מגיעים הנתונים מהשרת למסך?**
ה־React שולח בקשה (למשל `GET /api/recipes`), השרת שולף ממסד הנתונים, מחזיר JSON, וה־React שומר את התשובה ב־State (או ב־React Query) ומציג אותה. כשמשהו משתנה, למשל נוסף מתכון, ה־React מבקש את הרשימה מחדש.

**למה ההתראות לא מופיעות מיד, בלי לרענן?**
כי ה־React בודק התראות חדשות כל דקה או שתיים. התראות בזמן אמת דורשות טכנולוגיה נוספת (WebSockets), שלא נכללה כדי שהפרויקט יישאר פשוט.

**מה זה Migration?**
קובץ שמתאר שינוי במבנה מסד הנתונים. כך המבנה זהה בכל מקום: במחשב, בבדיקות ובענן.

**מה זה Swagger?**
תיעוד חי של כל ה־API, שמאפשר גם לנסות כל קריאה ישירות מהדפדפן. כדאי לנסות קריאה ב־Swagger לפני שכותבים אותה ב־React.

**במה השתמשת ב־AI?**
בבניית השרת ומסד הנתונים, כפי שמותר בדרישות הפרויקט. את קוד ה־React כתבתי בעצמי.
